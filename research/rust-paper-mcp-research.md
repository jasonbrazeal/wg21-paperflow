# Research Brief

Find the libraries, architecture patterns and data sources needed to build a Rust RAG system over the full WG21 paper corpus and expose its papers and metadata to LLM clients through an MCP server.

- **What is the most mature Rust SDK for building an MCP server, and which transports (stdio, streamable HTTP) and primitives (tools, resources, prompts) does it support?**
  - [modelcontextprotocol/rust-sdk (rmcp)](https://github.com/modelcontextprotocol/rust-sdk) - rmcp is the official Rust SDK for MCP, maintained under the modelcontextprotocol GitHub org. It runs on tokio and ships as two crates, `rmcp` and `rmcp-macros`. It implements the MCP 2026-07-28 spec and stays compatible with 2025-11-25. It also supports sampling, elicitation, roots, completions, subscriptions, tasks, pagination and OAuth. (HIGH)
  - [rmcp README: Transports](https://github.com/modelcontextprotocol/rust-sdk#transports) - Each transport sits behind its own Cargo feature. stdio is `transport-io`. The Streamable HTTP server is `transport-streamable-http-server`, which exposes `StreamableHttpService` as a Tower service you can mount on axum or hyper. Stateless Streamable HTTP mode is supported. (HIGH)
  - [rmcp README: Tools, Resources, Prompts](https://github.com/modelcontextprotocol/rust-sdk#tools) - Tools use the `#[tool]`, `#[tool_router]` and `#[tool_handler]` macros, and a tools-only server can use `#[tool_router(server_handler)]`. Resources are served by implementing `list_resources`, `read_resource` and `list_resource_templates` on `ServerHandler`. Prompts use the `#[prompt_router]` and `#[prompt]` macros, with arguments defined as structs deriving `JsonSchema`. (HIGH)
  - [crates.io: rmcp](https://crates.io/crates/rmcp) - The latest version is 3.5.1, released 2026-10-05, with about 35.7M downloads, which makes it the dominant Rust MCP crate. The 3.x line has breaking changes, covered by a migration guide in discussion #969 on the GitHub repo. (HIGH)
  - [rust-mcp-stack/rust-mcp-sdk](https://github.com/rust-mcp-stack/rust-mcp-sdk) - This is the main community alternative: version 2.0.0, with about 313K downloads, roughly 1% of rmcp's. It says it passes 100% of the official conformance tests and supports stdio, Streamable HTTP and backward-compatible SSE. Other options (pmcp, ultrafast-mcp, mcp-sdk) are smaller or stale. (MED)

- **Which Rust-native vector store and hybrid search options work best for a corpus of tens of thousands of technical documents that needs metadata filtering?**
  - [LanceDB Rust SDK: VectorQuery](https://docs.rs/lancedb/latest/lancedb/query/struct.VectorQuery.html) - LanceDB 0.40.0 is embedded and needs no server process. Its Rust API provides `full_text_search` (BM25, after you create an FTS index), `execute_hybrid` with RRF fusion by default, pluggable rerankers and SQL-style `only_if` filters. (HIGH)
  - [Metadata Filtering in LanceDB](https://docs.lancedb.com/search/filtering) - Pre-filtering is the default, and the same `where` filter applies to both the vector and FTS sides of a hybrid query. Post-filtering can return fewer rows than requested. The docs claim sub-100ms filtered search at billion-row scale, far beyond this corpus. (HIGH)
  - [Qdrant Hybrid Search](https://qdrant.tech/documentation/search/text-search/hybrid-search/) - Qdrant stores dense vectors and BM25 sparse vectors (with the IDF modifier) as named vectors on the same point, then fuses them in one query. Payload filtering and payload indexes are core features, and the Rust client is `qdrant-client` 1.19.0. It runs as a client-server deployment. (HIGH)
  - [Qdrant Edge BM25](https://qdrant.tech/documentation/edge/edge-bm25/) - Qdrant Edge (`qdrant-edge` 0.8.0) runs in-process with local BM25 sparse embedding (`EdgeBm25`). It is still in beta, so the API may change. (MED)
  - [tantivy and the DIY ANN option](https://crates.io/crates/tantivy) - You could build hybrid search yourself with tantivy 0.26.2 for BM25 and filterable fields, an ANN crate (usearch, arroy or hannoy) for vectors, and your own RRF fusion. That means more code and filtering across two indexes, compared with LanceDB or Qdrant doing it in one query. (MED)

- **How can embeddings be generated locally in Rust with open-weight models, without depending on a cloud API?**
  - [fastembed-rs](https://github.com/Anush008/fastembed-rs) - fastembed 7.1.1 handles dense, sparse and rerank models locally. It runs ONNX through `ort` with HF tokenizers and needs no tokio. It supports BGE, nomic-embed, mxbai, gte, snowflake-arctic, jina v2 and embeddinggemma, and runs Qwen3-Embedding behind an optional candle feature. (HIGH)
  - [Hugging Face candle](https://github.com/huggingface/candle/tree/main/candle-examples/examples) - candle-core 0.11.0 is a pure-Rust framework that runs on CPU, CUDA or Metal. Its examples cover bert, modernbert, nomic-bert, jina-bert, gte-qwen, nvembed_v2 and quantized-qwen3. It gives lower-level control than fastembed, and you handle pooling yourself. (HIGH)
  - [pykeio/ort](https://github.com/pykeio/ort) - ort is the ONNX Runtime 1.31 binding underneath fastembed. It is still at release candidate 2.0.0-rc.14, with no stable 2.x release yet, which is a risk to note when pinning dependencies. (MED)
  - [EmbedAnything](https://github.com/StarlightSearch/EmbedAnything) - EmbedAnything 0.7.1 is an embedding pipeline that runs on Candle or ONNX. It supports Model2Vec static embeddings and ingests PDFs and HTML directly. (MED)
  - [text-embeddings-inference (TEI)](https://github.com/huggingface/text-embeddings-inference) - TEI v1.9.4 is a self-hostable embedding and reranker HTTP server written in Rust, with Metal support. It fits if you want a separate service instead of embedding in-process. (MED)

- **What machine-readable sources exist for WG21 paper metadata, and how do they map to wg21.link and open-std.org?**
  - [wg21.link/index.json](https://wg21.link/index.json) - This is about 10 MB and holds roughly 29.3k entries, including 11,758 papers. Keys combine paper and revision (e.g. `P2300R10`). Fields are type, title, subgroup, author (one comma-joined string), date, link, long_link, source and an optional github_url. There is no mailing field, and there are no bare unversioned keys, so you have to compute the latest revision. It is also served as .ndjson, .yaml and .bib. (HIGH)
  - [wg21.link usage page](https://wg21.link/) - `/pXXXX` redirects to the latest revision and `/pXXXX/github` redirects to the tracking issue. `/pXXXX.yaml` returns citeproc metadata. An unlisted `specref.json` (about 9 MB) carries a split authors list. (HIGH)
  - [open-std.org yearly paper index](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/) - This is the only source with an explicit mailing assignment (`id="mailingYYYY-MM"`), mailing date, previous version and disposition. It is HTML only, so you have to scrape it. Paper files live in the same directory. (HIGH)
  - [cplusplus/papers issues](https://github.com/cplusplus/papers/issues) - The tracker has one issue per paper, with labels for target group and status, and you can query it through the GitHub REST API. Some linked issues have been deleted and return HTTP 410. (MED)

- **What chunking and retrieval strategies work well for long technical standards papers that contain code, wording diffs and revision histories, especially when one paper has many revisions?**
  - [VersionRAG (arXiv 2510.08109)](https://arxiv.org/abs/2510.08109) - Plain semantic RAG scores 58% on version-sensitive questions and GraphRAG scores 64%. A version-aware graph combined with routing by query intent (filter to a version, or track changes) reaches 90%, and indexing uses 97% fewer tokens than GraphRAG. (HIGH)
  - [Temporal Misgrounding in Legal RAG (arXiv 2608.09393)](https://arxiv.org/abs/2608.09393) - RAG over only the current version retrieved the applicable version 0% of the time, while a multi-version index reached 98.3% strict accuracy. Every revision should be indexed with version metadata. (HIGH)
  - [Adaptive Chunking (arXiv 2603.25333)](https://arxiv.org/abs/2603.25333) - Choosing a chunking method per document, scored on metrics that include block integrity (keeping code and tables whole), raised answer correctness to 72% from 62-64%. (HIGH)
  - [Contextual Retrieval (Anthropic)](https://www.anthropic.com/news/contextual-retrieval) - An LLM writes 50-100 tokens of document context, which is prepended to each chunk before both the embedding and the BM25 index. This cut failed retrievals by 49%, and by 67% with reranking. (HIGH)
  - [Azure RAG Chunking Phase](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-chunking-phase) - When a document's structure is known, the guide recommends splitting on that structure (headings, code blocks). Fixed-size chunks with overlap are a fallback. (MED)

The Rust stack is clear. rmcp is the official and dominant MCP SDK, and its Streamable HTTP server mounts directly on axum. LanceDB and fastembed together give an in-process stack with hybrid search (BM25, vectors and filtering) and no external services. Qdrant is the server-based alternative if operations or scale call for it. The main dependency risk is that `ort` 2.x, which sits underneath fastembed, is still a release candidate. The candle backend is the fallback.

On the data side, wg21.link's index.json is the clear choice for bulk metadata. It lacks mailing assignment and previous-version links, though, so you need to scrape the open-std.org yearly tables to get them. Several sources agree that you should index every revision with version metadata and chunk along document structure, instead of keeping only the latest revision or splitting into fixed-size chunks. Contextual prefixes (paper, revision and section) are a cheap way to make standalone code and wording-diff chunks retrievable.

Two questions are still open: how well these chunking strategies handle the mix of HTML, PDF and bikeshed formats across WG21 papers, and whether a version graph is worth building over simple revision metadata filtering.
